# Part 8 — GitOps (ArgoCD), DevSecOps & FinOps

This is the highest-differentiation section. Most mid-level candidates are weak here, so strong answers move you up a band.

---

## A. GitOps & ArgoCD

**1. What is GitOps, precisely?** Four principles: (1) the entire desired state is **declarative**, (2) it's **versioned and immutable** in Git, (3) changes are **pulled automatically** by an agent, (4) a controller **continuously reconciles** actual state toward desired and reports divergence. The key distinction from "CI that runs kubectl": reconciliation is continuous and pull-based, so drift is corrected, and Git is the audit log.

**2. Why is GitOps better than a push-based CI deploy?** (a) **Security** — CI never needs cluster credentials; the agent inside the cluster pulls, so you don't hand out kubeconfigs or open the API server to your CI provider. (b) **Auditability** — every change is a commit with an author and a review. (c) **Drift correction** — manual `kubectl edit` is reverted automatically. (d) **Disaster recovery** — rebuild a cluster by pointing ArgoCD at the repo. (e) **Consistency** across many clusters. Lead with the security argument; it's the one that persuades platform leadership.

**3. ArgoCD architecture.** `api-server` (API/UI/CLI), `repo-server` (clones repos and renders manifests — Helm template, Kustomize build), `application-controller` (compares rendered desired state to live state, patches, tracks health), plus optional `applicationset-controller`, `notifications-controller`, and Redis for caching. Understand that ArgoCD renders manifests itself — it does **not** use `helm install`, so Helm hooks and release state behave differently (a common real-world gotcha).

**4. Explain `Synced` vs `Healthy` vs `Degraded` vs `OutOfSync`.** Sync status compares live manifests to Git. Health is a per-resource assessment (built-in for Deployments/StatefulSets, plus custom Lua health checks for CRDs). You can be **Synced but Degraded** (manifests applied, pods crashlooping) and that's exactly the state that catches teams out — see the S6 scenario in Part 1. Promotion gates must check **Healthy**, not just Synced.

**5. Repository structure: how do you lay out a GitOps repo?** Separate **source code repo** from **config repo** (so an image bump doesn't trigger a code CI run and permissions differ). Config repo per environment or per cluster with directory overlays: `clusters/prod-eu/`, `apps/<service>/base/` + `overlays/prod/`. Avoid branch-per-environment — it invites merge drift and cherry-pick errors; use directories so all environments are visible in one diff. State the trade-off, since some orgs prefer branches for approval gating.

**6. What is the app-of-apps pattern and ApplicationSet?** App-of-apps: one parent Application whose manifests are other Applications — bootstraps a whole cluster from a single root. **ApplicationSet** is the modern replacement: generators (list, cluster, git directory, matrix, pull-request) template Applications automatically, so adding a directory or a cluster provisions an app with no manual wiring. PR generators give you ephemeral preview environments per pull request — a great thing to mention.

**7. Sync waves and hooks.** `argocd.argoproj.io/sync-wave` orders resources (negative first): CRDs and namespaces before operators, operators before CRs, DB migration Jobs before the app. `PreSync`/`Sync`/`PostSync`/`SyncFail` hooks run Jobs at lifecycle points — `PreSync` for migrations is the canonical example. Also `argocd.argoproj.io/hook-delete-policy` so hook Jobs don't accumulate.

**8. How do you handle secrets in GitOps?** You cannot commit plaintext secrets, so: **External Secrets Operator** (a `ExternalSecret` CR in Git, actual value pulled from AWS Secrets Manager/Key Vault/Vault at runtime) — the preferred answer, because Git holds only a reference. Alternatives: **Sealed Secrets** (encrypted with a cluster-specific key, safe in Git, but rotation and cluster-rebuild are awkward), **SOPS** with age/KMS (works well with `argocd-vault-plugin` or a Kustomize KSOPS generator). Explain the trade-off: ESO keeps Git clean and rotation external; Sealed Secrets keeps everything in Git but couples secrets to a cluster key.

**9. How do you stop ArgoCD fighting other controllers?** `ignoreDifferences` for fields owned by something else (HPA-managed `replicas`, webhook-injected sidecars, `metadata.annotations` written by a cloud controller), plus `syncOptions: ServerSideApply=true` to respect field ownership. Without this, ArgoCD and the HPA flap replica counts against each other forever.

**10. When would you *not* use auto-sync with self-heal?** Prod environments where you need a human approval gate, or during an incident where you're deliberately hand-patching (self-heal would revert your mitigation — so know that `argocd app set --sync-policy none` or a sync window is part of your incident toolkit). Common pattern: auto-sync + self-heal in dev/staging, manual sync with approval in prod. Also mention **sync windows** to block deploys during freeze periods.

**11. ArgoCD vs Flux — trade-off?** ArgoCD: rich UI/visualization, multi-tenancy via Projects, great for many teams and human-driven promotion. Flux: more composable controllers, lighter, native Helm release semantics, arguably better as a building block for a platform team. Both are CNCF graduated. Choose ArgoCD when developer self-service and visibility matter; Flux when you want a minimal, GitOps-toolkit approach.

**12. How does progressive delivery work with GitOps?** **Argo Rollouts** (or Flagger) replaces the Deployment with a `Rollout` CR supporting canary/blue-green steps, traffic shaping via ingress/mesh, and **AnalysisTemplates** that query Prometheus for error rate/latency and automatically promote or abort. This is the answer to "how do you deploy safely 50 times a day": automated, metric-driven rollback with no human in the loop.

**13. How do you do multi-cluster GitOps?** One ArgoCD "hub" managing registered remote clusters (simple, single pane, but a blast-radius and scaling concern) vs ArgoCD per cluster (isolation, but N control planes to manage). Use ApplicationSet cluster generators to fan the same app out with per-cluster values. Mention ArgoCD Projects + RBAC for tenancy, and that the hub's credentials to all clusters make it a high-value target requiring strong protection.

**14. How do you roll back in GitOps?** `git revert` the config commit — the reconciler does the rest, and the rollback is itself auditable. ArgoCD also has `argocd app rollback` to a previous sync revision for emergencies, but the Git-native path keeps Git as truth (otherwise the next sync re-applies the bad state — an important trap to name).

## B. DevSecOps

**15. What does "shift left" actually mean in practice?** Move security checks to the earliest point where they're cheap to fix, and make them part of the developer's normal loop rather than a gate at the end. Concretely, at each stage: **pre-commit** (secret scanning with gitleaks, lint), **PR** (SAST, dependency scan, IaC scan, license check, all as required checks), **build** (image scan, SBOM, signing), **pre-deploy** (admission policy verifying signature and policy compliance), **runtime** (drift/behaviour detection, network policy, CVE re-scan of running images). Key principle: findings must be **actionable and fast**, or developers will demand exceptions and you'll lose the control entirely.

**16. Name the scan types and what each catches.** **SAST** (source code flaws — SonarQube, Semgrep, CodeQL), **SCA/dependency** (known CVEs in libraries — Snyk, Dependabot, Trivy; this is where most real risk lives), **secret scanning** (gitleaks, trufflehog, GitHub secret scanning + push protection), **IaC scanning** (Checkov, tfsec, Trivy config, KICS), **container image scanning** (Trivy, Grype), **DAST** (running app — OWASP ZAP), and **runtime** (Falco, Defender for Containers). Know that SAST is noisy and SCA is high-signal — prioritizing accordingly is a maturity signal.

**17. How do you gate a build on security findings without blocking everyone?** Fail on **new**, **fixable**, **reachable** HIGH/CRITICAL only — not on the entire historical backlog. Baseline existing findings, then ratchet. Provide an auditable, time-boxed exception process with an owner and expiry (`.trivyignore` with a date and a ticket). Track mean-time-to-remediate as the real metric rather than raw vulnerability count. The judgement here is the answer: a gate that blocks 100% of builds gets switched off in a week.

**18. Explain software supply chain security.** Threats: compromised dependency, typosquatted package, malicious/compromised CI action, tampered artifact, compromised registry. Controls: **pin dependencies and actions by digest/SHA**, lockfiles with hashes, private registry/upstream proxy so you're not pulling live from the internet, **SBOM** (Syft → CycloneDX/SPDX) so you can answer "are we affected by CVE-X?" in minutes not days, **cosign** keyless signing + **SLSA provenance** attestations, and **admission-time verification** (Kyverno `verifyImages`, Ratify, Connaisseur) so an unsigned image can't run. Mention least-privilege CI: ephemeral runners, scoped OIDC tokens, no long-lived cloud keys, and read-only default `GITHUB_TOKEN`.

**19. What is SLSA and why should I care?** A framework of provenance levels describing how tamper-resistant your build is — build on a hosted, ephemeral, isolated builder that produces signed provenance saying "this artifact came from this source at this commit via this build process." It converts "trust me" into a verifiable claim, and it's what admission control checks.

**20. How do you secure a Kubernetes cluster end to end?** Answer in layers: **cluster** (private API endpoint or IP allow-list, RBAC least-privilege, audit logging shipped off-cluster, encrypted etcd, regular patching); **node** (minimal/hardened OS, no SSH, patch via node replacement not in-place, seccomp/AppArmor); **workload** (Pod Security Admission `restricted`, non-root, read-only rootfs, drop capabilities, no hostPath/hostNetwork, resource limits); **network** (default-deny NetworkPolicy, mTLS via mesh, egress control); **identity** (IRSA/Workload Identity, no static keys, short-lived tokens); **supply chain** (signed images, admission verification, scanned base images); **runtime** (Falco/eBPF detection, no `kubectl exec` in prod without audit); **secrets** (external store, encrypted at rest, rotation). Then: **detection and response** — you will be breached eventually, so know what your audit trail and containment plan are.

**21. What's the most commonly missed Kubernetes security issue?** Over-permissive ServiceAccounts and the default `automountServiceAccountToken: true` — every pod gets an API token it usually doesn't need. Set it false by default. Runner-up: cluster-admin handed out to CI, and a `hostPath` mount of `/` in a "debug" DaemonSet that never got removed.

**22. How do you handle a critical CVE announced on a Friday afternoon?** Structured response: (1) **Determine exposure** — query SBOMs/registry to find which images and running workloads include the package; that's why you generate SBOMs. (2) **Assess reachability and exploitability** — is the vulnerable path actually invoked, is it internet-facing, is there a known exploit? (3) **Mitigate fast** — WAF rule, feature disable, network policy, or scale-down, buying time before a rebuild. (4) **Patch and roll** — rebuild base images, canary, verify. (5) **Communicate** — clear status to stakeholders with a decision on whether this is a fix-now or Monday item, based on evidence, not panic. (6) **Retro** — how long did steps 1–2 take? If discovery took a day, the action item is inventory, not patching.

**23. Compliance in pipelines — how do you satisfy an auditor?** Evidence generated automatically: every change traceable to a reviewed PR (branch protection, CODEOWNERS, no direct pushes), separation of duties (author ≠ approver), immutable audit logs of who deployed what and when, policy-as-code that *proves* the control ran, and artifact provenance. The senior framing: **make compliance a by-product of good engineering**, so nobody spends a week screenshotting evidence before an audit.

## C. FinOps

**24. What is FinOps and what's the operating model?** A practice bringing financial accountability to variable cloud spend, run as a cycle: **Inform** (visibility, allocation, tagging, showback), **Optimize** (rightsize, eliminate waste, commit), **Operate** (governance, budgets, continuous improvement) — with a cross-functional team of engineering, finance, and product. The framing that matters: FinOps is about **unit economics and value**, not about spending less; the goal is efficient spend, and sometimes the answer is to spend *more* to make revenue or reliability.

**25. Walk me through cutting a cloud bill by 30%.** Do it in this order and say why: (1) **Measure and allocate** — tagging policy enforced by Azure Policy/SCP + AWS Cost Categories; you cannot manage what you can't attribute, and untagged spend is where waste hides. (2) **Kill obvious waste** — non-prod schedules (nights/weekends is ~70% of non-prod hours), orphaned disks/snapshots/EIPs/idle LBs, gp2→gp3, log retention, old-generation instances. Fast, zero-risk, no architecture change. (3) **Right-size** using real utilization (Compute Optimizer/Advisor, VPA recommendations, K8s requests vs actual usage — over-requesting is the dominant K8s waste). (4) **Improve density** — bin-pack the cluster, consolidate under-utilized node pools, Karpenter consolidation. (5) **Purchase discounts** — Savings Plans/Reserved/CUDs *after* right-sizing, laddered so you don't over-commit; spot for interruption-tolerant work. (6) **Architecture** — Graviton/ARM, caching to cut egress, VPC endpoints to cut NAT charges, lifecycle-tier storage, serverless for spiky workloads. (7) **Prevent regression** — Infracost in PRs to show cost delta before merge, budgets and anomaly alerts, and a per-team unit-cost dashboard. End with: I'd report **cost per 1,000 requests** or cost per tenant, because absolute spend rising while unit cost falls is a *healthy* business.

**26. What's the biggest source of waste in Kubernetes specifically?** Gap between **requests and actual usage**. Teams copy-paste requests, over-provision "to be safe," and the scheduler reserves that capacity whether it's used or not — so you pay for a cluster that looks 80% allocated and 20% utilized. Fix: VPA recommendations, dashboards comparing requests vs usage per namespace, Goldilocks/Kubecost/OpenCost for allocation and showback, and quota policy. Second: idle non-prod clusters. Third: cross-AZ traffic.

**27. How do you show cost per team in a shared Kubernetes cluster?** OpenCost/Kubecost allocating node cost by pod requests × runtime, keyed on namespace/labels, plus shared-cost distribution rules for control plane, ingress, and monitoring. Requires a labelling standard enforced at admission. Then showback first (visibility changes behaviour on its own), chargeback only if the org is ready for it.

**28. When is it right to spend *more*?** When reliability, security, or engineer time is worth more than the infra cost — bigger CI runners to cut developer wait, multi-AZ redundancy, keeping a warm standby to meet RTO, or paying for a managed service instead of operating your own. Being able to argue *against* a saving with a business case is a strong senior signal; blind cost-cutting that causes an outage is a net loss.

**29. How do you set up cost governance without slowing teams down?** Guardrails not gates: budgets with anomaly alerts routed to the owning team, policy blocking absurd instance types or untagged resources at deploy time, default-safe module presets (right-sized, tiered storage, auto-shutdown in non-prod), cost visibility in the PR. Teams get autonomy inside a sane envelope, and finance gets predictability.

**30. What's the intersection of FinOps and sustainability?** Same lever, different metric: higher utilization, ARM/efficient instances, right-sizing, and region choice (carbon intensity of the grid) reduce both cost and emissions. Cloud carbon dashboards let you report it. Worth a sentence — it increasingly appears in platform-team objectives.
